# Decisiones

## Tomadas

| Id | Decisión | Por qué |
| --- | --- | --- |
| D-01 | **Repositorio propio**, separado del panel de gestión | Cada aplicación propia tiene su repositorio. Además, el panel controla Docker sin login: si respondiera bajo `/__menu/` en todos los nombres, cualquier página de cualquier aplicación podría enviarle formularios que pasarían su comprobación de mismo origen. |
| D-02 | **Insertar un script con un plugin de Traefik**, no envolver las aplicaciones en un iframe | La mayoría de aplicaciones prohíben que las carguen en un iframe de otro origen. Con un iframe la dirección del navegador no reflejaría la aplicación, y no funcionaría al entrar directamente por el nombre de cada una. |
| D-03 | **Script en el mismo origen**, bajo `/__menu/`, con una ruta de Traefik de alta prioridad que lo envía al servicio en cualquier nombre | Las aplicaciones con CSP suelen permitir solo scripts de su propio origen; un script de otro nombre lo bloquearían. |
| D-04 | **Shadow DOM y JavaScript sin framework** para el menú | Aísla los estilos en los dos sentidos y mantiene el script pequeño. |
| D-05 | **Go con la librería estándar** para el plugin y el servicio | Traefik ejecuta los plugins en Go con un intérprete (Yaegi) que solo admite la librería estándar. El servicio sigue la misma línea. |
| D-06 | **La lista sale de la API de Traefik**, no de las etiquetas de Docker | Incluye las rutas declaradas en ficheros, como los servicios aún no migrados, y el servicio no necesita acceso a Docker. |
| D-07 | **Las rutas de los servicios miran solo el principio del nombre**, como en el resto del hub (`` HostRegexp(`^nombre\.`) ``) | El dominio no aparece en ningún repositorio: el menú construye los enlaces con el dominio de la página actual. Las reglas `` Host(`nombre.completo`) `` se enlazan tal cual. |

## Pendientes

| Id | Pregunta | Opciones y recomendación |
| --- | --- | --- |
| P-01 | **Cómo llega el plugin a Traefik** | *Plugin local*: Traefik lo lee de una carpeta montada, sin descargas, pero hay que decidir cómo llega esa carpeta al servidor (por ejemplo, copiada desde la imagen del servicio a un volumen). *Catálogo de plugins*: Traefik lo descarga de GitHub por su etiqueta al arrancar; es más sencillo de versionar, pero Traefik depende de Internet al arrancar. Recomendación: plugin local, si la forma de llevarlo al servidor no complica el despliegue. |
| P-02 | **Dónde se activa la inyección** | *Global*: middleware en la entrada web de Traefik, con la lista de exclusiones en la configuración del plugin; cubre también los servicios declarados en ficheros. *Por servicio*: una etiqueta en cada stack. Riesgo: si Traefik no puede cargar el plugin, los routers que usan el middleware dejan de responder; con el middleware global, todas las aplicaciones a la vez. Recomendación: global con exclusiones, porque el menú debe aparecer en todo, pero llegar a ello de forma gradual: primero por servicio en un par de aplicaciones y, cuando esté probado, global, con el procedimiento para quitarlo documentado en el repositorio de despliegue. |
| P-03 | **Cómo consulta el servicio la API de Traefik** | A través de la ruta del panel de Traefik, con la cabecera de su nombre, o por una entrada interna de Traefik sin publicar. Recomendación: la que no obligue a exponer nada nuevo. |
| P-04 | **Cómo se ocultan aplicaciones** | *Configuración* del servicio, versionada en el repositorio de despliegue. *Desde la interfaz*, guardando la lista en el servicio, lo que exige que solo se pueda cambiar desde casa o con algún control. Recomendación: configuración en la primera versión y valorar la interfaz después. |
| P-05 | **Móvil** | Ocultarlo por debajo de un ancho de pantalla, o mostrarlo con una opción. Hay que decidir el umbral, y si en tablet en vertical sigue apareciendo. |
| P-06 | **Dónde se guarda la posición del botón** | *Cookie en el dominio común* de las aplicaciones: la misma posición en todas. *Almacenamiento local del navegador*: una posición por aplicación, porque cada nombre es un origen distinto. Recomendación: cookie en el dominio común, que cumple RF-05. |
| P-07 | **Idioma del código** | El panel de gestión usa identificadores en español; las aplicaciones más recientes, en inglés, y la interfaz de plugins de Traefik ya está en inglés. Recomendación: código en inglés, documentación e interfaz en español. |
| P-08 | **Qué se muestra de cada aplicación** | El principio del nombre (`jellyfin`), un nombre legible configurado aparte o el título de la página. Iconos: el favicon de cada aplicación o ninguno. Recomendación: el principio del nombre en la primera versión, y nombres e iconos con las categorías. |
| P-09 | **Qué hacer con las CSP que bloquean el script** | Aceptar que en esas aplicaciones no hay menú, o que el plugin ajuste su CSP. Recomendación: no tocar CSP en la primera versión; comprobar en el entorno de pruebas qué aplicaciones lo bloquean. |
| P-10 | **Compresión que el plugin no sabe descomprimir** | La librería estándar de Go trae gzip, pero no Brotli ni zstd. *Quitar `Accept-Encoding`* en las peticiones de página, para que la aplicación responda sin comprimir, y volver a comprimir con el middleware de compresión de Traefik. *Dejar solo gzip* en `Accept-Encoding`, descomprimir, insertar y volver a comprimir en el plugin. *Dejar pasar sin menú* lo que no sea gzip. Recomendación: quitar `Accept-Encoding` solo en las peticiones de página, que son pequeñas; el resto conserva su compresión. |
| P-11 | **Qué cuenta como página y dónde se inserta el script** | Hay que separar las páginas de los fragmentos HTML que piden las propias aplicaciones (htmx y similares). Recomendación: solo GET con `Sec-Fetch-Dest: document` (o `Accept` con `text/html` si el navegador no la envía), respuesta 200 con `Content-Type: text/html` y sin `Content-Range`. El script se inserta con `defer` justo antes de `</head>`, buscándolo en los primeros kilobytes para no cargar la página entera; si no aparece, la respuesta pasa sin tocar. |
| P-12 | **Quién puede ver la lista de aplicaciones** | La ruta `/__menu/` tiene prioridad sobre las de las aplicaciones en todos los nombres, así que se salta la autenticación que tenga cada una: cualquiera que llegue a una página de login podría leer la lista. *Pública*. *Con la misma protección que el resto del hub* (autenticación o limitación a la red de casa). Recomendación: separar el script, que no contiene datos y puede ser público, de la lista, que va en otra ruta para que el despliegue la proteja como quiera. Si la lista no carga, el botón no aparece. |
| P-13 | **Dominio común para la cookie de la posición** | El script no sabe por sí solo cuál es el dominio común (`app.casa.example.co.uk` frente a `app.example.com`). *Deducirlo* quitando el principio del nombre, coherente con D-07. *Configurarlo* en el servicio, que se lo pasa al script. Recomendación: deducirlo, con la opción de fijarlo por configuración; si la página está en una IP o en un nombre sin dominio, la posición se guarda solo en ese origen. |
| P-14 | **Orden y apertura de los enlaces** | Orden alfabético o configurable. Abrir en la misma pestaña o en una nueva. Recomendación: alfabético y en la misma pestaña, como un menú de navegación; con Ctrl o Cmd el navegador ya abre en otra. |
| P-15 | **Caché del script** | La dirección del script es fija en todas las páginas, así que una versión nueva tarda en llegar si el navegador lo guarda en caché. *Revalidar siempre* (`no-cache` con `ETag`). *Versión en la dirección*, lo que obliga a cambiar la configuración del plugin en cada versión. Recomendación: revalidar siempre; el script es pequeño y la respuesta 304 es casi gratis. |
| P-16 | **Versión de Traefik** | Para qué versión se desarrolla y se prueba el plugin. Recomendación: Traefik v3, la que se use en el hub, fijada en el entorno de pruebas. |
| P-17 | **Licencia** | El repositorio es público y no tiene licencia. Recomendación: MIT. |
